# ZeroTask Major Upgrade - Forensic Architecture Audit & Implementation Blueprint

This blueprint outlines the current architecture, database model, security controls, and feature gaps identified in the ZeroTask mobile codebase and Supabase backend. It defines the implementation roadmap for the major product upgrade.

### Critical Security Findings & RLS Vulnerabilities:
1. **Meeting Invitee Visibility Bug**: The `meetings` table has only one SELECT policy: `Users can view meetings they organized` (`organizer_id = auth.uid()`). A participant added to `meeting_participants` **cannot** select the corresponding meeting details from the `meetings` table. This breaks meeting calendar views for invitees.
2. **Missing Tenant / Company Scoping**: Multi-tenancy is entirely implemented as client-side filters. Because there is no `company_id` or `organization_id` on the `tasks`, `projects`, or `meetings` tables, any user who gets a department UUID of another tenant could select their data. RLS doesn't isolate tenant orgs.
3. **Broad User Profile Select**: The RLS policy `Users can view all profiles` is set to `USING: (auth.role() = 'authenticated'::text)`. Any authenticated user can read all users from other companies.

## 4. Task System Architecture

- **Creation**: Handled by management (`Founder`, `Department Head`, `Manager`). Tasks can be assigned to a department (`department_id`) or left global.
- **Assignment**: Stored in a separate table `task_assignees`.
  - Assigner rules are enforced via the `can_assign_task(assignee_id, assigner_id)` function.
  - Managers can assign tasks only to Employees in their department.
  - Department Heads can assign to Managers and Employees.
- **Multiple Assignees**: Supported at the schema level because `task_assignees` is a bridge table.
- **Activity & Auditing**:
  - The `tasks_audit_trigger` trigger logs structural events (`TASK_CREATE`, `TASK_UPDATE`, `TASK_DELETE`) to the `audit_logs` table.
  - The `tr_task_activity` trigger inserts timeline items (`task_created`, `task_assigned`, `status_changed`) into `execution_activity` for visualization in the app.
  - **Audit Gap**: Changes in the `task_assignees` relationship table (such as a Manager adding an assignee) do not trigger entries in `audit_logs`.

## 5. Execution Portal Gap Analysis

> [!NOTE]
> **Current Status**: **NOT CURRENTLY IMPLEMENTED**
> There is no execution team role, table, or restricted view structure in the application.

### Proposed Architecture:
- **Tenant Entity**: We need to introduce a `companies` or `organizations` table to support scoped vendor/partner assignments, rather than relying on plain-text names.
- **New Role**: Add `Execution Partner` or `Execution Team` role to the user roles.
- **Task Visibility isolation**:
  - Update `tasks` and `task_assignees` schemas to support partner assignments.
  - Add `assigned_company_id` to tasks.
  - Write new RLS policies allowing Execution Team users to see *only* tasks assigned to their specific company, without seeing other internal company folders or department lists.
- **Ambiguities requiring business clarification**:
  - *Are Execution Team members external vendors, or internal departments?*
  - *Do we need a full multi-tenant model with separate billing/organization IDs?*

## 6. Meeting Section Gap Analysis

> [!NOTE]
> **Current Status**: **PARTIALLY IMPLEMENTED**
> The `meetings` table, calendar view, and participant linkage exist. However, the system lacks video links, notifications sync, and calendar API hooks.

### Gap Analysis:
1. **Zoom & Teams Integrations**: **NOT CURRENTLY IMPLEMENTED**. There are no columns to store virtual event URLs or OAuth tokens for these platforms.
2. **Participant RLS Select**: As detailed in section 3, participants cannot read meeting details of meetings they did not organize.
3. **Meeting Status**: Missing a `status` column to track cancellations or reschedules.

### External Credentials Required:
- **Zoom**: Zoom App Marketplace credentials (OAuth client ID and secret) supporting Server-to-Server OAuth or standard OAuth flow.
- **Microsoft Teams**: Microsoft Azure AD application ID, secret, and tenant details with Microsoft Graph API scopes (`Calendars.ReadWrite`, `OnlineMeetings.ReadWrite.All`).

## 8. Self-Assign Gap Analysis

> [!NOTE]
> **Current Status**: **PARTIALLY IMPLEMENTED**
> RLS and database validation functions currently allow Founders, Department Heads, and Managers to self-assign tasks. Employees are blocked by RLS policies on `task_assignees`.

### Gap Analysis:
- **Employee Permission**: Employees cannot self-assign tasks from the backlog.
- **Audit Logs**: Assigning oneself to a task via `task_assignees` is not logged in the `audit_logs` table (only changes to `tasks.user_id` trigger it).

## 9. WhatsApp Integration Gap Analysis

> [!NOTE]
> **Current Status**: **NOT CURRENTLY IMPLEMENTED**
> No code, webhooks, or configuration columns for WhatsApp exist in the system.

### Proposed Integration Architecture:
- **User Database Update**: Add `phone_number` and `whatsapp_enabled` columns to the `users` table.
- **Webhook Gateway**: We must integrate an external API provider like Twilio WhatsApp Business API or Meta WhatsApp Cloud API.
- **Message Dispatcher**: Create a Supabase Edge Function `/send-whatsapp-notification` triggered by database events (e.g. task assignment, deadline reminders) using pg_net.

## 10. Recommended Implementation Order

To minimize regression risks and build features logically, we recommend the following delivery phases:

### Phase 1: Security Hardening & Bug Fixes (Relational RLS)
1. **Fix Meeting RLS**: Update `meetings` SELECT policy to allow select access if the user is organizer OR in `meeting_participants`.
2. **Audit logging update**: Add triggers to `task_assignees` to log assignments in `audit_logs`.

### Phase 2: Self-Assign Capability
1. **Update `task_assignees` RLS**: Add policy allowing employees to insert assign records where `user_id = auth.uid()` and task department matches employee department.
2. **Frontend UI update**: Add a "Claim Task" button on the task details screen.

### Phase 3: Tenant Schema & Execution Portal
1. **Database Migration**: Create `organizations` table. Add `organization_id` foreign key to `users`, `tasks`, and `projects`.
2. **Execution Role**: Update RLS to restrict users with the `Execution Team` role to their own company's assignments.

### Phase 4: Meeting Links (Zoom / Teams Integrations)
1. **Azure & Zoom Integration**: Implement OAuth link handlers.
2. **Dynamic Meetings**: Trigger API requests to generate Zoom/Teams meeting rooms during meeting creation.

### Phase 5: Reporting Upgrades
1. **Historical RPCs**: Create date-range parameterized analytical functions.
2. **Export Service**: Implement file generation (CSV/PDF) using Expo sharing handlers.

### Phase 6: WhatsApp Notifications
1. **WhatsApp Cloud API Integration**: Create edge triggers mapping user actions to WhatsApp message templates.
